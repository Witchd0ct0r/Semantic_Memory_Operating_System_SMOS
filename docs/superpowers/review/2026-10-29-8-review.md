# BM25 and Benchmark Error Analytics Review

**Date:** 2026-10-29  
**Reviewed range:** `20b5a59..HEAD`  
**Review basis:** package 8, BM25 design and plan, implementation, differential and lock tests, benchmark error analytics, and full test suite.

## Findings

### 1. Important — One SQLite connection is accessed under independent locks

The smoke benchmark's intermittent `SystemError: error return without exception set` at `VectorStore.bump_recall`'s `commit()` is consistent with concurrent use of the same `sqlite3.Connection` through two unrelated locks. `VectorStore` serializes its operations with `VectorStore._lock`, while `GraphStore` serializes its own methods with `GraphStore._lock`; neither lock excludes the other. A graph operation and a memory operation can therefore interleave statement execution and transaction commits on the shared connection. An unfinished cursor may contribute, but the observed evidence does not establish it as the cause, and the stress attempt described in the package did not reproduce the error. This review cannot attribute the exact `SystemError` to one interleaving.

**Location:** `smos/memory/vector_store.py:40,52-56`; `smos/memory/graph_store.py:20-24,28-34,43-49`; `smos/memory/vector_store.py` methods that execute or commit through `self._db`, including `bump_recall` at `smos/memory/vector_store.py:324-338`.

**Suggested fix:** Give every operation on this connection one shared reentrant lock and use it consistently in both stores, including multi-statement transactions and cursor consumption. A separate SQLite connection per store is another sound boundary, but requires checking transaction and WAL behavior. Add a concurrent graph-write / recall-update regression test that verifies both error-free completion and transaction isolation.

### 2. Minor — Duplicate UUIDs in `build()` are removed differently from the old index

`_load` retains every input row and its postings, but `_slot_of` maps a duplicate UUID to only its last slot. A later `remove(uuid)` therefore kills the last row. The reference implementation removes the first matching row; its `remove_batch` removes all rows with that UUID, while the new slot map can kill only one. For example, building `[("x", "alpha"), ("x", "beta"), ("y", "alpha beta")]` and removing `"x"` leaves the wrong duplicate alive and changes subsequent rankings. Normal VectorStore IDs are unique, but the public index's old behavior accepted duplicate IDs and the package specifically includes this input in scope.

**Location:** `smos/memory/bm25_index.py:78-102,126-140`; comparison behavior in `tests/bm25_reference.py` `remove`/`remove_batch`.

**Suggested fix:** Define and enforce duplicate-ID behavior in `build()` (for example, reject duplicates or deduplicate consistently), or retain enough per-ID slot information for mutations to reproduce the reference behavior. Add explicit duplicate-ID build, remove, and remove-batch cases to the differential tests.

### 3. Minor — Transport exceptions in quality and latency probes abort before the error digest is saved

The mixed-load workers catch request exceptions and add them to `ErrorLog`, but `quality_probes` and `latency_probe` only record HTTP responses. A reset, disconnect, or timeout raised by `conn.request` escapes those functions. The runner then stops the temporary server in its `finally` block but exits before it summarizes errors and writes `result.json`. A failed benchmark caused by a dropped probe connection can consequently lose the exception details this release is intended to preserve.

**Location:** `smos/bench/httpload.py:172-190,209-243`; result/error persistence in `smos/bench/runner.py:183-200`.

**Suggested fix:** Catch and record transport exceptions in these probe loops, then continue or return a partial probe result; alternatively, persist a partial error summary in the runner's failure path before re-raising. Keep the existing behavior unchanged when `errors=None` if that remains part of the API contract.

### 4. Minor — ExceptionGroup digests retain only the final leaf

When parsing a grouped traceback, `add_server_log` overwrites one `leaf` variable as it encounters later bar-prefixed lines, then records only that value at the closing separator. A group with multiple independent child exceptions is summarized as only its last child. The current grouped-traceback test covers a single child, so it does not detect this loss.

**Location:** `smos/bench/errorlog.py:69-100`; single-child coverage in `tests/test_bench_errorlog.py:160-171`.

**Suggested fix:** Parse and count each child exception leaf, respecting the existing exception cap, or explicitly represent the group as one grouped error with all child types summarized. Add a multi-child and nested-group parser test.

## Checks that looked sound

- The BM25 implementation matched the reference across the existing random corpora, operation sequences, negative-idf and degenerate-query cases. Tie ordering, zero-score padding, repeated query terms, and the negative-weight full-sort path are covered. The duplicate-ID build case above is the identified gap.
- The read-write lock's writer preference and exception cleanup look consistent; the direct lock tests and the full concurrent API tests passed. I found no lock-order cycle in the examined BM25 call paths.
- Postings use `float32` term frequencies, so integers above 2^24 are not represented exactly. Reaching that count requires over sixteen million occurrences of one term in one memory; typical corpus segmentation makes this an extreme input, and no practical ranking discrepancy was established. The int32 slot ceiling is beyond realistic store sizes.
- The error digest stores cleaned exception messages rather than request headers or tokens, reads logs line by line, and applies exception/group caps. Stored error values are converted to text and escaped by the report's normal Jinja rendering; I found no template injection path in the inspected errors section.
- `SMOS_TORCH_THREADS` remains unset by default, preserving the prior default. The setting is validated at warm-up and applied on the encode calling thread; no concrete thread-pool defect was established in this review.
- The calibration values are explicitly provisional, but two runs of identical code are not enough to estimate tail variability robustly. Repeated paired runs and a spread estimate would make the thresholds more defensible. `query_p95_ms` from 100 samples is a noisy comparison metric; retain it as a useful tail indicator, but pair it with p50 or a mean and avoid treating one p95 change as a stable regression.
