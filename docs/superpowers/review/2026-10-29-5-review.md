# SMOS Release Fingerprint, Batching, and Graph Migration Review

**Date:** 2026-10-29  
**Reviewed range:** `c042d4c..HEAD`  
**Review basis:** package 5, implementation, migration and retrieval tests, release docs, and update-verification record.

## Findings

### 1. Minor — The version-literal regression test misses stale version strings

`test_rebuild_files_carry_no_version_number` searches only for the current `smos.__version__`, although its name and comment promise to catch any version literal in the rebuild fingerprint. With the package at `0.3.1`, changing `compose.yaml` back to `image: smos:0.2.0` passes this assertion; the two-manifest test also copies that same file into both snapshots and passes.

**Reproduction:** Keep `smos.__version__ = "0.3.1"` and set the Compose image to `smos:0.2.0`. The version-literal test searches for `0.3.1`, not `0.2.0`, and the release-only-version test sees identical Compose contents in both manifests.

**Location:** `tests/test_versioning.py:18-27,30-48`; current image expression at `compose.yaml:9`.

**Suggested fix:** Assert that rebuild-sensitive files contain no `X.Y.Z` version literal (or pin the allowed Compose image expression exactly), rather than searching only for today's package version.

### 2. Minor — The chunking test does not prove that SQL parameter chunks are used

`test_get_many_chunks_beyond_the_sql_variable_limit` lowers the application chunk constant to four but never checks the number of SQL statements or lowers SQLite's actual variable limit. An implementation that puts all 12 UUIDs into one `IN` clause would still pass under SQLite's normal 999-parameter limit.

**Reproduction:** Replace the chunk loop with one `WHERE uuid IN (...)` query and run the existing test with its 12 IDs. The query stays below SQLite's default parameter limit and returns the expected records, so the test passes without chunking.

**Location:** `tests/test_query_batching.py:45-49`.

**Suggested fix:** Assert that the trace callback observes `ceil(len(ids) / chunk_size)` SELECTs, or set the connection's variable limit below the input size before calling `get_many`.

### 3. Minor — The “existing 0.3.x graph” migration test builds its fixture with the migration under test

The test named `test_graph_tables_migration_adopts_existing_current_tables` calls the current `_graph_tables` migration to create the supposed pre-existing tables, then verifies that the migration runner advances the version. It does not independently pin the schema written by the previous `GraphStore._init_schema`, so a future schema drift between old installations and this migration could go undetected by this test.

**Reproduction:** Change the old GraphStore table definition in a way that differs from `_graph_tables`, while leaving the migration-generated fixture unchanged. This test still creates and reuses the migration's own schema; it never opens a database made with the old definition.

**Location:** `tests/test_migrations.py:119-133`.

**Suggested fix:** Build the fixture from the exact pre-migration GraphStore DDL (or keep a small database fixture produced by 0.3.0), then run migration 3 and assert its rows and indexes survive.

## Checks that looked sound

- **Rebuild fingerprint:** `pyproject.toml` obtains its version from `smos.__version__`; Compose uses the configurable image tag; the Dockerfile has no versioned header. The dynamic version source is present in `smos/` before the Dockerfile's `pip install --no-deps .` step, so the setuptools attribute lookup has its source. `manifest.py` hashes the rebuild files and model tree in Git-compatible order; `test_repo_rebuild_files_match_git_head` passed in this checkout. A mutable default image tag (`latest`) makes old images less convenient to select by tag after repeated rebuilds, but I found no updater rollback regression: its code/data rollback runs within the current image, and Docker retains the old image ID unless pruned.
- **Batched reads:** `_query_internal` holds the vector-store lock across FAISS search and `_rows_by_row_id`, and that helper does not reacquire the non-reentrant lock. The helper and `get_many` split parameters into 500-ID chunks; query-hit order is restored by iterating the original FAISS hit list, and missing rows are skipped. Hydration callers preserve their previous missing-record behavior and score handling. The remaining per-neighbor lookups are bounded by the selected result count and neighbor window; I found no unbounded N-query path introduced by this change.
- **Graph migration:** A valid 0.3.0 store at schema version 2 with intact graph tables advances to version 3 while preserving rows. The node-check and edge-check legacy shapes are rebuilt inside the migration transaction; renamed-table indexes are dropped with the old table and the node type index is recreated. The tables have no foreign-key references that would make the rename/drop sequence unsafe. Fresh stores create graph tables before `GraphStore` is constructed.
- **Already-version-3 incomplete schema:** If a database claims schema version 3 but its graph tables were later dropped, the migration runner has no pending migration and `GraphStore` no longer recreates them at every open; graph operations will fail. This is an inconsistent/corrupt schema rather than a normal 0.3.x upgrade shape. Consider validating required tables at startup and failing with a clear repair message, rather than silently serving until a graph request fails.
- **Release 0.3.0 / review 4 resolutions:** The release metadata and workflow removal match the supplied release notes. The update-verification resolution table records the five review 4 fixes, and the corresponding rollback marker, stale-pending guard, SHA-bound confirmation, request-closing gate, and negative CPU-counter guard are present in the reviewed base.
