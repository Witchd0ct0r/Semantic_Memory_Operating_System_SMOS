# Benchmark Page Review

**Date:** 2026-10-29  
**Reviewed range:** `8e1013d..HEAD`  
**Review basis:** package 7, design and plan, benchmark verification record, implementation, and the full test suite.

## Findings

### 1. Important — A `bench-tmp` junction can redirect cleanup outside the data directory

`safe_run_dir` rejects `base.is_symlink()` but does not reject a Windows junction at `data_dir/bench-tmp`. On the review runtime (Windows, Python 3.13), a junction has `Path.is_symlink() == False`; `base.resolve()` follows it, so the child path comparison succeeds. I created a junction from a temporary data directory to a separate temporary target and confirmed `safe_run_dir(data_dir, 1)` accepted the external `.../1` directory. Startup recovery or cleanup can then remove that numeric directory outside the SMOS data tree.

**Location:** `smos/bench/service.py:51-63`, especially the base check at 56-62; startup cleanup calls it at 197-203.

**Suggested fix:** Reject junctions and other reparse points for the base as well as symlinks (for example, use `Path.is_junction()` where available and a platform-safe reparse-point check). Verify containment against the unresolved trusted data directory, not only against the resolved base.

### 2. Important — Orphan recovery can kill an unrelated SMOS process with a prefix-sibling data path

`_kill_orphans` identifies a runner when a command-line argument `startswith(marker)` and a server when `SMOS_DATA_DIR.startswith(marker)`. A stale run directory under `.../bench-tmp/` is enough to trigger the scan; an unrelated server using `.../bench-tmp-other/data` then matches the prefix and is killed. I reproduced this with a sleeping Python process whose `SMOS_DATA_DIR` was the adjacent `bench-tmp-other/data`; recovery terminated it as an orphan.

**Location:** `smos/bench/service.py:207-230`.

**Suggested fix:** Normalize and resolve both paths, then require a path-component containment check (such as `relative_to(base)` with an explicit equality policy), rather than string-prefix matching. Add a test for a sibling directory whose name begins with `bench-tmp`.

### 3. Important — The updater and benchmark interlocks have a check-then-set race

`Updater.begin` checks `benchmark_active` before acquiring its own busy lock and setting updater state to `staging`. Concurrently, `BenchmarkService.start` checks `updater.state()` and then sets `benchmark_active`. If the updater reads `False`, the benchmark checks `idle` and sets its flag, and then the updater advances to `staging`, both operations proceed. The update can stage and hand over while the benchmark is active, contrary to the mutual-refusal contract; handover may then cancel and interrupt the run during shutdown.

**Location:** `smos/update/apply.py:80-93`; `smos/bench/service.py:131-141,247-259`.

**Suggested fix:** Serialize both transitions with one shared interlock, and recheck the opposing state while holding it before either operation commits to `staging` or `benchmark_active`.

### 4. Important — Failure to start the watcher leaves a live runner and maintenance flag behind

After `_launch` starts the child process, `start` stores it in `_active` and starts the watcher thread outside the guarded `try` block. If `Thread.start()` raises (for example, the process cannot create another thread), no watcher owns cleanup: the runner remains alive, `_active` remains set, and `benchmark_active` remains true. The runner's parent watchdog does not help while the service process is still alive, so the API remains in maintenance until restart.

**Location:** `smos/bench/service.py:131-142`.

**Suggested fix:** Treat watcher creation as part of launch. If it fails, kill and reap the runner family, remove the work directory, mark the run failed where possible, clear `_active`, and always clear the maintenance flag.

### 5. Important — A failed result write leaves a `running` row that blocks every later benchmark

`_store` catches and logs any exception from `finish_run`, then returns normally. `_watch` subsequently clears `_active` and `benchmark_active`, but the database row can remain `running`. `_check_can_start` treats any such row as an active run, so the page appears idle while every later start is refused until the service restarts and startup recovery marks the row interrupted. Disk-full or a transient SQLite error at completion can trigger this path.

**Location:** `smos/bench/service.py:341-352,411-422`; the stale-row refusal is at `smos/bench/service.py:247-254` and `smos/admin/benchmarks.py:62-63`.

**Suggested fix:** Retry storing a minimal final failure state after a result-write failure, or reconcile stale `running` rows in the live service before refusing a new run. Keep the cleanup and API flag reset in a `finally` path.

### 6. Minor — Mixed-load latency omits failed reader requests

`_load` computes latency percentiles from successful requests and separately counts errors. `mixed_step` returns only the successful-request p95 and RPS for the two reader phases; it discards both phases' error counts and client-limited flags. A mixed-load run with many failed reads can therefore show a deceptively low p95 without reporting that those reads failed.

**Location:** `smos/bench/httpload.py:256-264,273-299`; the report chart displays the reduced fields in `smos/admin/benchmark_view.py:76-85`.

**Suggested fix:** Include read error counts (and client-limited status) for both phases in the result and data table, and label p95 as successful-request latency.

### 7. Minor — The reported “peak” server RSS is only a post-probe sample at each size

The runner assigns `peak_rss` from one `memory_info().rss` reading after the latency probe at each size, then stores the maximum of those samples as `peak_server_rss_bytes`. It does not sample during ingest, HNSW construction, server startup, or load, so a transient memory peak can be missed even though the stored field is labeled peak. The chart's text says “after the latency probe,” but the run details expose the raw `peak_server_rss_bytes` key.

**Location:** `smos/bench/runner.py:121-126,147-152`; display in `smos/admin/benchmark_view.py:283-290` and `smos/admin/templates/benchmark_report.html:112-120`.

**Suggested fix:** Sample RSS through each phase and record a real maximum, or rename the field everywhere to make clear it is a post-probe sample.

### 8. Minor — The RAM estimate and install note undercount the benchmark's model copies

The live API process loads a model at startup. The runner also loads one through `phases.ingest_to`/`embed`, and retains it; then `BenchServer` starts a second API process that warms another model. During server phases this is two additional model copies, while the install note describes one extra copy. The current free-memory check (`1.5 GiB + 6 KiB per segment`) can therefore approve a run whose actual model footprint is materially higher than the page's explanation suggests.

**Location:** `smos/bench/service.py:66-79`; model use in `smos/bench/phases.py:32-48,51-70,141-147`; server startup in `smos/bench/httpload.py:92-110`; `smos/api/main.py:10-15`; user-facing note in `docs/INSTALL.md` under “The benchmark page.”

**Suggested fix:** Avoid holding both benchmark-process models at once if possible, or include both additional processes in the RAM estimate and state the true peak requirement in the page and install guide.

## Checks that looked sound

- The gate covers the `/api/v1` prefix, including the protected OpenAPI and docs handlers; `/api/v1/health` remains available. Requests increment the in-flight counter before the gate and the benchmark drains admitted API requests before launch.
- Runner authorization requires the one-time secret hash and a work directory directly under `bench-tmp`; the secret is passed through the environment rather than argv. The admin routes are session-protected and both POSTs check CSRF.
- The timed retrieval path returns the same result ids as `build_context` in the exercised tests. Exact and HNSW search use the same reconstructed vectors, normalized queries and configured `efSearch`; the report discloses that projections are extrapolations and quality probes are synthetic.
- Chart and table builders escape stored labels, series names and cell text before their generated SVG/table strings reach the template's `|safe` sites. Other stored strings use normal Jinja autoescaping.
- The verification record marks Standard and Full, Debian process behavior, and non-Chrome PDF printing as pending rather than completed.
