# SMOS Self-Update Review

**Date:** 2026-10-28  
**Reviewed range:** `ede8ab5..HEAD`  
**Review basis:** package 4, self-update design and plan, release/install docs, implementation, and tests.

## Findings

### 1. Critical — A crash during rollback can restart the new code without completing data restoration

The supervisor writes the snapshot completion marker before the update and trusts it on every restart, but rollback restores files in place without a rollback phase marker. If the process stops partway through `restore_data`, the next start sees the still-present `pending.json` and the old `.complete` token, skips restoration, and starts the target overlay against a partially restored data directory.

**Reproduction sequence:** Start an update and let the new code migrate `metadata.db`; make its health check fail so rollback begins; stop the supervisor while `restore_data` is copying snapshot entries; restart with `pending.json` still present. `snapshot_matches` remains true, so `_apply_pending` proceeds to the target overlay without finishing the restore. The new process can report healthy on a mixture of old and migrated files, breaking the code/data rollback guarantee and risking user data.

**Location:** `smos/launcher.py:265-282` trusts the snapshot marker on restart; `smos/launcher.py:297-306` restores data without recording rollback progress.

**Reproduced:** No; this is a restart-path defect visible from the supervisor state transitions. Existing tests cover a completed rollback and restart after migration, but not interruption during the restore itself.

### 2. Important — A pending update bypasses stale-overlay handling after an image rebuild

`Supervisor.run()` handles `pending.json` before calling `active_overlay`, so a pending staged release from an older image is applied and stamped with the *new* image's `build_id`. This bypasses the stale-code protection and can leave an older overlay running over a newly rebuilt image, including one with different dependencies or data schema.

**Reproduction sequence:** On image build A, stage release `0.3.0` and leave `pending.json` plus its staging directory on the volume by stopping the container before the supervisor applies it. Rebuild/pull image B with baked version `0.4.0` and restart with the same volume. `_apply_pending` accepts the old staged `0.3.0`, sets its `base_build_id` to build B, and can keep it as the active overlay after a successful health check.

**Location:** `smos/launcher.py:228-237` chooses the pending path before stale-overlay validation; `smos/launcher.py:253-280` applies the pending version and associates it with the current build id.

**Reproduced:** No; the pending-update branch does not compare the staged update's originating build with the current build. Existing stale-overlay tests exercise only `active_overlay` without `pending.json`.

### 3. Important — Confirmation binds only the release version, not the displayed commit SHA

The update confirmation page displays the release commit SHA, but its form submits only the version, and `Updater.begin` re-evaluates the release and checks only that the version is unchanged. If the release tag moves to another commit with the same `__version__` after the page is shown, the admin's confirmation silently applies code from the new SHA.

**Reproduction sequence:** Show the admin `v0.3.0` at SHA A; move that tag to SHA B with the same package version; submit the existing confirmation form. The fresh evaluation resolves B, the version still matches `expected_version`, and the archive for B is installed without asking the admin to review its SHA.

**Location:** `smos/admin/templates/update.html:41-52` shows the SHA but posts only `version`; `smos/admin/pages.py:243-247` passes only that version; `smos/update/apply.py:106-122` validates only the version.

**Reproduced:** No; the request and comparison fields establish the mismatch. The tests assert the SHA is displayed and the version is passed, but do not simulate a moved tag between display and apply.

### 4. Important — New read requests can enter after the drain check and race database closure

The exit thread waits for `inflight` to reach zero once, then closes the stores and exits, while maintenance mode still admits GET requests. A read that enters after the zero check can use a store or admin connection while `app.state.close()` closes it, producing a failed request during the update window.

**Reproduction sequence:** Let `_exit_when_drained` observe `inflight == 0`; before it closes the stores, start an authenticated `GET /api/v1/query` or an admin dashboard GET. The maintenance middleware admits that read, but the exit thread can close the database before the request finishes.

**Location:** `smos/update/apply.py:158-169`; read requests remain admitted by `smos/api/app.py:195-207`.

**Reproduced:** No; the race is between the final counter check and `close()`. The tests cover draining existing requests and allowing reads during maintenance separately, but not a read arriving at that boundary.

## Checks that looked sound

- **Archive and GitHub handling:** Archive member paths reject absolute paths, backslashes, drive prefixes, and `..`; only regular allowed-suffix files below `smos/` are written, with file, count, unpacked-size, and archive-size caps. Extraction failures remove staging. The URL path uses configured repo data and a validated full SHA; redirects require HTTPS except same-origin loopback test redirects. TLS verification remains on and the custom CA only adds trust anchors. JSON and release notes are capped. I found no request, release-note, or tag value that directly selects a filesystem path or arbitrary download URL.
- **Versions and rebuild detection:** Strict tags and package version checks prevent mismatched-version installation; lower/equal releases are not offered. The manifest compares the expected Git object IDs for the rebuild-sensitive files, including `smos/launcher.py`; missing target entries force rebuild. `releases/latest` follows GitHub's creation-order semantics as documented, and the release checklist directs maintainers to publish only increasing versions. The SHA confirmation gap is reported above.
- **Access control and rendering:** All four update routes require an admin session; both POST routes verify CSRF. API tokens alone do not authorize the pages. Release notes use normal Jinja escaping in `<pre>`, and the inline script serializes its values with `tojson`. Health exposes only the running version in addition to its existing status response.
- **Maintenance and audit:** API writes are gated by `require_write`; admin and claim mutations are blocked by the maintenance middleware; reads remain available by design. The request counter uses `finally`, and existing non-streaming routes decrement it on errors as well as success. Migration 4 adds `update_log` without changing earlier migration behavior. Audit import is serialized and idempotent by completion timestamp. The drain race above remains.
- **Supervisor and packaging:** Normal success, health failure, wrong-version health, and completed rollback restore the intended code and data; `.complete` is written only after a snapshot copy finishes. The launcher forwards stop signals and relays child output; the image runs it as the non-root entry point. The test suite covers these ordinary paths, but not interruption during rollback or stale pending state across a rebuild.
- **Earlier review fixes:** The unauthenticated usage-log cap/path normalization and worker-thread dashboard handling are present in the current code. The reference-counted document locks and batched pruning changes remain intact. I found no new regression in those fixes.
