## Open items / blockers

- **DEFECT in v0.3.0 (found while writing this handoff, not yet fixed):** the rebuild fingerprint includes `pyproject.toml` and
  `compose.yaml`, but BOTH carry the version number (`version = "0.3.0"` in `pyproject.toml`, `image: smos:0.3.0` in `compose.yaml`),
  and every release must bump them (`tests/test_versioning.py` forces `pyproject` = `__version__`). So **every future release differs
  from the installed image in those two files and would be shown as "needs a rebuilt image"; no release could be applied in place.**
  The unit and end-to-end tests did not catch it because they publish fake releases whose manifest equals the image's. Fix options
  (preferred first): (a) make the version single-sourced: `pyproject.toml` `dynamic = ["version"]` with
  `[tool.setuptools.dynamic] version = {attr = "smos.__version__"}`, and `image: smos:${SMOS_IMAGE_TAG:-latest}` (or a fixed tag) in
  `compose.yaml`, so these files only change when dependencies/packaging change; (b) hash those files with the version line removed
  (not possible against GitHub's blob ids without downloading the files). Add a regression test that computes the manifest for two
  consecutive "releases" differing only in `smos/__init__.py` and expects `available`, and update `docs/RELEASING.md` and
  `tests/test_versioning.py` and `tests/test_packaging.py` (they currently assert the version in `pyproject.toml`).
- Governor-side checks still pending on Debian: `docker compose down && up` persistence, and a read-only token being refused on upload.
- Known, accepted: Swagger UI loads from a CDN; GraphStore creates its tables outside the migration runner; one shared SQLite
  connection per database; update trust root is GitHub TLS plus the repo owner's account; the snapshot is a full copy of the data dir.
